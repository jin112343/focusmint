最終仕様は **512×512・sRGB・WebP quality 88**。すべて正方形で、引き伸ばしはしない。生成プロンプト・方法は `generated-prompts.json`、採用結果とハッシュは `visual-review.json` にある。

## 容量とデコード計測

| 項目 | 旧画像 | 最終画像 |
|---|---:|---:|
| トレーニング画像数 | 291 | 291 |
| 画像ファイル合計 | 43,368,029 bytes | 10,325,582 bytes |
| 画像ファイル削減率 | — | **76.19%** |
| 1枚あたりの最大デコード画像メモリ | 67,699,984 bytes | 1,048,576 bytes |
| 全画像を各1回デコードしたRGBA合計 | 480,144,440 bytes | 305,135,616 bytes |

上記メモリは画像ピクセルのRGBA容量で、アプリ全体のRAM使用量や同時使用量ではない。比較は旧画像の原寸デコードと、新画像の表示寸法に制限したデコード。テストホストの計測であり、端末のフレーム時間ではない。

768px候補では小さい旧画像より初回デコード処理が増えたため、表示に必要な鮮明さを確認して512pxを採用した。512px候補の1回の比較では、全件のデコード合計0.628秒→0.584秒、最大99.7ms→4.9ms。小さい旧画像は個別には速く、中央値は旧0.98ms、新1.81msだった。すべての画像の読み込みが速くなるという主張はしない。計測の詳細は `decode-benchmark.json`。

## 再実行

Pythonの専用環境へ `tool/requirements-image-tools.txt` の依存を入れる。キーはリポジトリ外のファイルに保存し、本文をログやチャットへ出さない。

```sh
python tool/generate_training_images.py --dry-run
python tool/generate_training_images.py --env-file /path/to/private.env --out-dir /path/to/masters
```

生成にはインストール済みImageGenスキルのCLIを使用し、CLI自体は変更していない。生成入力は `replacement-jobs.jsonl`、再生成入力は `regeneration-jobs.jsonl`、最終採用プロンプトは `generated-prompts.json`。生成後は全件を目視確認し、`tool/optimize_training_images.py` で512pxへ揃え、テストを再実行する。プロバイダー・モデル・品質・価格を変える場合は、予算の前提も再確認する。


お問い合わせ機能の仕様とメール通知は `Backend/README.md` を参照。採用画像の元データと配布バイナリはリポジトリ外に保存し、秘密情報・署名情報・中間ビルドをコミットしない。
